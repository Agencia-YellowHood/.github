# Guia de Integração / Onboarding Guide 🚀

Bem-vindo à equipe de tecnologia da **Agencia YellowHood**! Este manual contém orientações essenciais sobre como usar a organização, nossas diretrizes de conduta e fluxo de trabalho.

---

## 🇧🇷 Português - Guia de Integração

### 1. Fluxo de Trabalho (Git Workflow)
Adotamos uma abordagem simplificada do Git Flow. Toda alteração de código deve ser feita em uma branch dedicada e nunca diretamente na `main`.

*   **Convenção de Nomes de Branches**:
    *   `feature/nome-recurso` para novos recursos (ex: `feature/login-google`).
    *   `bugfix/nome-correcao` para correção de erros em desenvolvimento.
    *   `hotfix/correcao-urgente` para correções rápidas diretamente em produção.
*   **Pull Requests (PR)**:
    *   Sempre abra um Pull Request para fundir seu trabalho na `main`.
    *   Adicione uma descrição clara explicando o que foi alterado.
    *   Todo PR deve passar por pelo menos 1 revisão de código (Code Review) antes de ser aceito.

### 2. Padrões de Código e Conduta
*   **Código Limpo**: Escreva nomes de variáveis explicativos em inglês, funções pequenas e evite duplicações.
*   **Documentação**: Mantenha o arquivo `README.md` de cada serviço atualizado de acordo com o modelo de templates.
*   **Respeito e Cooperação**: Respeite os prazos, colabore nas revisões de código de forma construtiva e tire dúvidas com o time no canal do Slack/WhatsApp sempre que necessário.

## 🇺🇸 English - Onboarding Guide

### 1. Git Workflow
We use a streamlined version of Git Flow. All code modifications must be committed in a dedicated branch and never directly to the `main` branch.

*   **Branch Naming Convention**:
    *   `feature/feature-name` for new features (e.g., `feature/google-login`).
    *   `bugfix/bug-description` for development bug fixes.
    *   `hotfix/urgent-patch` for immediate production patches.
*   **Pull Requests (PR)**:
    *   Always submit a Pull Request to merge your branch into `main`.
    *   Write a concise summary detailing the changes made.
    *   Every PR requires at least 1 Code Review approval before it is merged.

### 2. Coding Standards & Code of Conduct
*   **Clean Code**: Write descriptive variable names in English, design small reusable functions, and avoid code duplication.
*   **Documentation**: Ensure that the `README.md` of your active service matches the official template structure.
*   **Collaboration & Respect**: Respect timelines, provide constructive feedback during code reviews, and reach out to the team via Slack/WhatsApp whenever you need help.
